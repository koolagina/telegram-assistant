# Локальные окна lecture-кодов — 28.10.2026

Код: `tools/lecture_windows.py`; тесты: `tests/test_lecture_windows.py`. Контроллер использует существующий `assistant_access.py`. Это локальное ядро: Telegram/QR web form/identity registry и запись XLSX не подключены. Ни одного реального сообщения или отметки в журнале не создано.

## Сценарий и гарантии локальной модели

- `open(context, lecture_id, request_id)` проверяет текущую policy: private Telegram, права на свою lecture или явное session-specific замещение. Новое окно длится ровно 90 секунд и целиком помещается в подтверждённую пару и срок замещения.
- Часы берутся из серверного clock provider контроллера. Интервал [opened_at, expires_at), в момент expires_at код уже не действует. Нельзя продлить код повторным запросом. Откат относительно последнего зафиксированного серверного времени блокирует операцию и требует проверки часов.
- SQLite `BEGIN IMMEDIATE` сериализует открытие. Запросы двух преподавателей через отдельные соединения получают одно активное окно на lecture. Стабильный request ID восстанавливает результат после перезапуска/потерянного ответа. Истёкший request не создаёт новое окно; требуется новое явное действие. На следующем окне код не повторяется в пределах той же lecture.
- `show(context, lecture_id)` повторно проверяет права и показывает только действующий код, не открывая и не продлевая окно. Восстановление уже открытого окна возможно и когда до конца пары осталось меньше 90 секунд; новое окно в таком случае запрещено.
- Код создаётся `secrets.randbelow`, четыре ASCII-цифры с ведущими нулями. Он хранится в SQLite только как AES-GCM ciphertext и keyed verifier, без plaintext в обычном аудите. AEAD связывает код с ID, временем, источником, исходным operator/binding и grant: изменение expires в БД не продлевает действие.
- При изменении состава/времени/типа/источника lecture нужна сверка, а не перепривязка существующего окна. `зач`, practice, cancelled, unknown, неverified и неполные группы закрыты. Сохраняются назначенный преподаватель, фактический открывший operator и substitution grant; это аудит операции, не доказательство физического нахождения преподавателя в аудитории.
- Отзыв исходного binding/замещения блокирует не только показ кода, но и новые регистрации в его окне. Полномочия перепроверяются по актуальному provider snapshot. Окно с отозванным operator не передаётся автоматически другому преподавателю; до истечения/сверки восстановление не подменяет происхождение.

## Регистрация — локальные факты, не готовая студенческая форма

`register(lecture_id, student_id, code)` разрешён **только после доверенного сопоставления академической личности** будущим адаптером. Передавать student_id напрямую из HTTP/QR запроса нельзя. Постоянный QR и форма пока отсутствуют; четырёхзначный код остаётся слабым подтверждением участия, его можно переслать.

Контроллер проверяет активного Student, действующий Enrollment нужной дисциплины/группы, подтверждённую текущую lecture, права исходного operator, целостность/срок окна и код. Ошибки кода и недоступность данных возвращают минимальный отказ. Для подтверждённой личности ограничены 5 неудачных проверок за фиксированную минуту на lecture+student; счётчик переживает перезапуск. Это не заменяет сетевое/IP/device rate limiting и защиту от перебора нескольких имён в будущей публичной форме. Fixed-minute limiter допускает соседние пачки около границы минут — строгий sliding limit здесь не обещается.

Локальная таблица attendance имеет уникальный ключ lecture+student. Повторная регистрация и несколько окон не создают второй факт; прежний факт сохраняет исходное окно/enrollment. Receipt сообщает `journal_status=not_synced` независимо от успешности регистрации. Нет writer/upload/mail transport и автоматического плюса в XLSX. Отработка и оценивание не реализованы этим модулем.

## Приватное состояние и ключ

- Нужна явная отдельная SQLite DB и project namespace. Каталог 0700, файл 0600, без symlink для файла/непосредственного каталога. `.lecture-state/` и SQLite artifacts исключены из Git.
- Ключ AES-GCM: ровно 32 bytes, поступает из защищённого runtime storage. В production ключ **не создавать заново при перезапуске**. В коде/тестах нет настоящего ключа: используется только явно синтетический fixture key.
- Ключ не хранится в DB и не печатается. Wrong key/project/schema дают отказ; не обходить ошибку новой пустой базой. Ключ, DB и проект должны восстанавливаться согласованно. При потере ключа старые коды не восстанавливаются из одной DB.
- WAL/FULL и транзакции обеспечивают локальные checkpoint/уникальность. Нужен один устойчивый общий файл; разные копии DB на нескольких машинах не координируются. Backup через SQLite backup API/остановленный процесс, не копирование одного main-файла при активном WAL.
- Таблицы содержат личные псевдоидентификаторы и историю операций. Не добавлять их в Git, публичные логи и отчёты. Retention/backup/rotation ключа — следующие эксплуатационные задачи. Истёкший ciphertext может оставаться в истории: 90 секунд — ограничение серверной проверки, не обещание физического стирания bytes на диске.

## Что должен сделать будущий transport

1. Проверить реальный Telegram sender/private callback и загрузить актуальный подтверждённый registry/verified фактическую lecture. `Context` или role от пользователя не доверять. Full AcademicReadGrant не даёт права открытия чужой lecture без substitution.
2. Связать стабильный server-owned request token с конкретной кнопкой/lecture/аккаунтом. Не использовать произвольный request_id из клиентского JSON и не считать один новый callback_id доказательством нового явного намерения после истечения старой кнопки.
3. Отдельно вести outbox/delivery: потерянный ответ Telegram не открывает новое окно. Можно повторно показать то же ещё действующее окно, не продлевая его. API acceptance не означает прочтение; если преподаватель не успел увидеть код, новое окно требует нового явного действия.
4. Форму регистраций защитить network rate limiting, серверным временем и registry resolver без раскрытия списков студентов. Она не даёт доступа к `/progress`.
5. После отдельной sandbox-приёмки подключать queue синхронизации в журнал. Успех локального факта не объявлять плюсом в журнале и не фиксировать дату отмены бонуса до реального принятого запуска.

## Зависимость и проверки

Для шифрования нужна `cryptography`; Google SDK не требуется:

```bash
python -m pip install -r requirements-lecture.txt
python -m unittest discover -s tests -p 'test_lecture_windows.py'
python -m unittest discover -s tests -p 'test_*.py'
node tests/run-current.cjs
```

Результаты: **22/22 windows PASS**, **138/138 всего Python PASS** (64 НВГУ + 16 XLSX + 36 policy + 22 windows), **101/101 Node PASS**. Набор windows также запущен в существующем отдельном venv с pinned cryptography 50.0.2; pip check успешен. Основной runtime содержит 50.0.0, на нём прошёл полный suite. Никаких новых credentials/настроек среды не добавлено.

Первый запуск был красным без модуля. Позднее четыре красных сценария воспроизвели: registration после revoke исходного operator, после revoke substitution, подмену expiry в DB и невозможность безопасного retry ближе к концу пары. Все исправлены. Ещё один дефект теста исправлен после случайного совпадения цифр кода внутри случайного window_id: теперь проверяется whitelist аудита и отсутствие code-value, а не ненадёжный substring по всему тексту.

Реальный Telegram/QR, authentication, актуальность источника, права реальных преподавателей/студентов, устойчивость production storage, сетевая защита и XLSX не проверены. Это локальная реализация ядра, а не включённая функция бота.
