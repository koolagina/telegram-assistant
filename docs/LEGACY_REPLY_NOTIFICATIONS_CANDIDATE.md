## Изменения и данные

`processMessage_`: план до добавления ответа/входящего; отправка только после сохранения и обновления поручения. При повторе — восстановление полей, затем обработка существующего плана.

Три новых helper: `legacyReplyNotificationSheet_`, `prepareLegacyReplyNotifications_`, `flushLegacyReplyNotifications_`. Используются существующие `withScriptLock_` и `appendOnce_`. Не заменяется весь кандидат 2.0.5, прежние исправления сохраняются.

Новый технический лист **«Уведомления ответов»**, шесть колонок:

| Колонка | Содержимое |
|---|---|
| Ключ | Уникальный ключ исходного сообщения и роли адресата |
| Payload JSON | Фиксированные адресат и текст; признаки исходного сохранённого ответа для сверки |
| Статус | PREPARED / SENDING / API_CONFIRMED / UNKNOWN |
| Telegram message ID | Идентификатор из проверенного ответа API |
| Обновлено | Время записи состояния |
| Ошибка | Только фиксированный код REVIEW_REQUIRED |

Лист содержит копию текста уведомления, имени, ссылки и ключей исходного ответа. Это реальные данные внутри существующей закрытой книги при будущей установке; нельзя публиковать содержимое в Git/артефактах. Изменение назначения хранения требует отдельного разрешения. Автоматическая очистка/TTL не предусмотрены; политика хранения остаётся отдельной задачей.

Перед отправкой проверяются весь набор адресатов, уникальность ролей, схема, JSON, актуальный адрес владельца и соответствие сохранённому ответу. Повреждение любого элемента блокирует отправку до API. План нельзя молча пересоздать по новому адресу. Форматы бизнес-листов не меняются. Payload хранится JSON, без формул в текстовых ячейках.

## Ограничения и следующий этап

Кандидат не гарантирует exactly-once всего обработчика. Нет автоматического повтора UNKNOWN, восстановления старых потерянных уведомлений, интерфейса ручного решения или политики архивации. Исходы SENDING/UNKNOWN переводят исходное обновление после штатных попыток в DEAD без повторных отправок; последующие updates продолжают обрабатываться. Нельзя очищать эти строки и вслепую replay/reset — иначе исчезнет доказательство предыдущей попытки.

ScriptLock защищает только согласованно работающие скрипты, не ручную сортировку/редактирование между проверкой и записью. Это сохраняющийся риск; строки технического листа нельзя сортировать во время обработки. Не перепривязывать адресаты и не сбрасывать статусы вручную.

Для следующего live-этапа требуется согласование установки одного source и нового листа, затем строго отдельный review/apply маршрут, свежая сверка, зашифрованный backup и независимый reread. Маршрут Google пока не расширен. Рабочий poll/триггеры/рассылки этим кандидатом автоматически не запускаются.
