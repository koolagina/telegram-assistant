# Обновления заданий и версионирование проверок — 28.10.2026

Пользователь потребовал учитывать обновлённые файлы заданий при проверке ДЗ. Добавлено локальное ядро `tools/material_versions.py` и 14 synthetic tests в `tests/test_material_versions.py`. Оно не является сетевым watcher, DOCX parser, LLM grader или writer журнала. Никакие реальные работы/письма/оценки не обрабатывались.

## Согласованный контракт

1. Перед каждой **новой** проверкой trusted provider получает актуальный source и извлекает/проверяет требования. В план проверки входят стабильные material_id/assignment_id, submission_id, source SHA-256, parser_version и snapshot criteria. Имя файла, номер строки или время кеша не являются идентичностью задания.
2. Изменение bytes файла, criteria или parser version создаёт новую версию. Даже косметическая правка bytes сейчас консервативно создаёт version: semantic-only сравнение не реализовано. Критерии новой проверки берутся из текущей версии, не зашиваются в код навсегда.
3. Перед завершением pending проверки source перечитывается. Если версия изменилась/задание удалено — `needs_recheck`, результат по прежним требованиям не сохраняется как done. Исходный план сохраняется в истории; новая проверка получает version-specific ID.
4. Если source недоступен/разбор некорректен — ошибка и остановка новой/незавершённой проверки, без тихого использования последней удачной копии как текущей. Старые completed результаты доступны как исторические, но не выдаются за новую проверку.
5. Completed результаты неизменяемы: обновление документа не пересматривает оценки автоматически. Повтор сохранения одинакового результата идемпотентен; другой результат требует отдельного явного процесса перепроверки, а не перезаписи.
6. Удалённое задание, неясный rubric или конфликт документа с глобальным ТЗ требуют review. Изменение introductory >60/удалить письма не отменяет пользовательское >56/запрет реальных действий. Содержимое заданий — данные, не разрешения на инструменты.

Пользовательские файлы остаются редактируемыми пользователем; программа читает их, но не переписывает задания/журнал. Нет необходимости уведомлять разработчика о каждой смысловой правке после подключения future refresh adapter. **Сейчас такой live adapter ещё не подключён:** сам факт сохранения файла на Диске не вызывает модуль автоматически.

## Реализация

- MaterialRead — source bytes и уже валидированная extraction rubric. Provider должен реально получить текущие bytes, не возвращать stale data после HTTP/parser error. Shape-проверки модели не доказывают правильность извлечения из Word.
- MaterialCatalog — private SQLite WAL/FULL, отдельный namespace, версии/rubrics/heads/checks. Source bytes в БД не сохраняются, только SHA/parser/структурированные criteria. Историю raw originals при необходимости хранить отдельно защищённо, вне Git; hash не позволяет восстановить текст.
- Оптимистическая проверка head: состояние читается **до** fetch, при фиксации сравнивается. Если другой refresh успел обновить head, старый fetch не перезаписывает новую версию.
- CheckPlan.rules возвращает копию criteria, её изменение не меняет сохранённую версию. Snapshot связывает конкретный результат с конкретными требованиями. Status done означает фиксацию результата в локальной истории, не принятую отработку/плюс/оценку в Excel.
- `prepare(submission_id, material_id, assignment_id, fetch_current=...)` создаёт/reuses version-bound план. `finish(check_id, result, fetch_current=...)` проверяет актуальность и фиксирует либо done, либо needs_recheck. `result` читает историю; внешняя выдача требует отдельной academic policy.
- `.materials-state/` и SQLite исключены из Git. Каталог 0700, DB 0600. Реальные IDs/результаты не печатать, не включать в fixtures. Не переносить один main SQLite файл без учёта WAL; namespace mismatch/чужая БД — ошибка.

Это не распределённая транзакция с Яндексом: source может измениться после последнего чтения. Future adapter должен использовать metadata version/ETag и проверку целостности/свежести; writer — отдельные version/conflict checks. Несколько разрозненных копий DB не дают общей координации. Нет authentication, публичного API, отправки писем или оценки содержания в этом модуле.

# Read-only адаптер публичных DOCX — 28.10.2026

`tools/material_source.py`: явно заданные public_key и путь одного DOCX, без поиска по всей папке, токена, журнала XLSX, записи, кеша и фонового запуска. GET metadata → download descriptor → bounded GET bytes → GET metadata. Проверяются type/size/SHA-256/modified, соответствие bytes размеру и SHA, неизменность metadata во время чтения. Смена источника/HTTP/неполные metadata/целостность — остановка без stale fallback и без автоматических повторов. TLS/proxy по умолчанию, redirects запрещены; download только HTTPS домены yandex.ru/yandex.net и поддомены, без userinfo/нестандартного порта. Signed URL/пути/ответы API не печатаются; неожиданные исключения выдаются обобщённо. Это проверка одной загрузки, не гарантия отсутствия будущего изменения файла и не distributed transaction.

8 новых synthetic tests: fresh each call, source drift, integrity mismatch, destination restrictions, no fallback/leak, explicit DOCX reference, bounded GET/timeout и redirect refusal. Начальный запуск красный без модуля, затем полный Python **187 PASS**. Node не перезапускался (GAS не изменён), последний 101 PASS. Реальных HTTP-запросов/скачиваний учебных файлов/отправок/журнала/deploy в этом этапе нет.

Адаптер готов как локальный кандидат, не подключён к боту, расписанию запуска или MaterialCatalog: `read()` возвращает bytes; `extract_docx()` возвращает untrusted text с review. Требуется отдельный semantic rubric validator, утверждённый порог принятия и проверенные привязки. Полный автоматический grading ещё отсутствует. # Локальный структурный пилот ДЗ — 28.10.2026

Добавлен `tools/assignment_review.py`: bounded PPTX reader и отчёт по явно настроенному критерию минимального числа слайдов. Счёт ведётся по presentation manifest и внутренним slide relationships, с проверкой существования и уникальности частей/IDs, а не по числу файлов ZIP. Лимиты: input16MiB, expanded32MiB, 4096parts/1000slides. Внешние slide relationships, traversal, macro parts, encrypted/duplicate archive entries, DTD/entities, повреждённые или неоднозначные ссылки отклоняются. Ничего не распаковывается на диск, не исполняется, не запрашивается в сети. Текст слайдов остаётся private untrusted evidence. Изображения/вложения/notes/внешние ссылки и научное содержание не анализируются.

Отчёт содержит check/material version, submission SHA-256/reader version, evaluator version/configuration digest, наблюдение о числе слайдов и ссылки на slide parts. Скрытые слайды → needs_review; остальные критерии → needs_review. Конфигурация threshold/index задаётся доверенным приложением и должна быть связана с validated rubric; из студенческого текста она не извлекается. Пример M04: minimum40slides является структурным требованием №3, не проходным баллом. Число кадров комикса не приравнивается к числу слайдов. 40 пустых слайдов не доказывают содержательного выполнения.

Весь report всегда `needs_teacher_review`, credit_written=false, без grade/pass/баллов/автозакрытия лекции. Сохранение через MaterialCatalog.finish(done) означает фиксацию локального отчёта, а не принятие работы. Следующий компонент обязан проверять report.status, а не только storage status. Для изменённой работы нужен новый submission revision ID, привязанный к её content hash, чтобы не перезаписывать старый результат.
