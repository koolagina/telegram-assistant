## Что входит в один пакет

| Часть | Результат |
|---|---|
| Отправка поручения | Адресат до API; долговременные plan/claim/API ACK; восстановление даты и статуса без повторной отправки |
| Приём текста или файла | Существующие реальные функции очереди, привязки, file guard, записи ответа и восстановления проверены совместно на моках |
| Уведомления об ответе | Раздельные адресаты и квитанции; неизвестный исход не вызывает повторной отправки |
| Личные задачи /add | Включён ранее подготовленный постоянный Telegram-ID и защита дублей |
| /approve и /revoke | Включён ранее подготовленный запрет повторной мутации прав старыми командами и повторов студенческих уведомлений |
| Диагностика | Включены read-only probe заголовков и runner, без пользовательских строк и записей |

Ранее установленное поведение ответов/файлов/уведомлений не переписывается заново. Новый код отправки заменяет только sendPendingTasks и добавляет два helper. Остальные изменения — уже отдельно проверенные кандидаты /add и команд доступа плюс read-only probe. Это не установка всего кандидата 2.0.5 и не изменение архитектуры на три мессенджера.

Сборщик: `tools/clasp/workflow-candidate.cjs`, функции composeWorkflowSource/buildWorkflowCandidate. Публичный diff: `patches/task-workflow-package.patch`. Исходные версии сохранены. Сборщик проверяет точный SHA-256 восьми исходных файлов, целевой main, синтаксис и коллизии; не изменяет вход. Повторное применение и drift отклоняются. По умолчанию привязан к последнему подтверждённому установленному снимку; тестовый override хеша существует только для локальных synthetic fixtures, не для обхода будущего live review.

## Найденные в сквозном сценарии дефекты

Два новых теста воспроизвели ошибки до исправления отправки. Обычный путь установленного source проверен отдельным тестом.

| Дефект | Причина | Исправление | Проверка | Риск после исправления |
|---|---|---|---|---|
| Поручение принято API, но дата/статус не восстановились | Успех внешней операции не имеет долговременной квитанции | ACK до финальной проекции; следующий запуск только восстанавливает поля | Сбой даты, финального статуса, принятый ACK с исключением — PASS | Если ACK не сохранился, требуется сверка |
| Потеря адресата при позднем сбое | chat ID записывался после отправки и части статусов | Адресат записывается до API, ID повторно разрешается перед проекцией | Отказ адресата до API, сортировка во время API — PASS | Ручная правка между последней проверкой и setValue не атомарна |
| Возможный повтор после неопределённого send | Нет разделения намерения и подтверждения API | CLAIM до API, без ACK повтор запрещён | Unknown API, invalid receipt, claim accepted → exception — PASS | Возможен пропуск при claim без фактического send; не считать его доставкой |
| Дубликаты/смена адресата могут направить ответ не туда | Неустойчивая идентичность | Проверка уникальности ID/студента, неизменности плана и адресата | Коллизии, ручной конфликт, старый uncertain status — PASS | Ручное удаление квитанций разрушает историю |

Новые task ID без исходного ID формируются через UUID и сохраняются один раз; существующие ID сохраняются. Завершённые отправки с датой/адресатом пропускаются без чтения квитанции каждой задачи. Старые строки «Ошибка отправки»/«Отправляется» без нового плана не мигрируют в автоматический повтор.

## Сквозной стенд

`tests/helpers/task-workflow.cjs` исполняет собранный Apps Script в vm, используя in-memory Sheets/Drive/Properties/Telegram/LockService. Он не подменяет business handler, storeFile_ или восстанавливающие функции: вызывается их настоящий код. Подменены внешние сервисы и часы. Семантика ведущего апострофа Sheets моделируется явно; её реальный bounded probe ранее выполнен отдельно владельцем. Полный реальный workflow этим не доказан.

Стенд проходит sendPendingTasks → очередь callback/message → processCallback_/processMessage_ → Drive guard → ответ/проекция → технические уведомления. Проверяются повторный запуск с сохранённым состоянием, отказ доступа, text-only и file/caption, сортировки, дубликаты, частичные записи, неизвестные API и DEAD без повторного файла. Одна неизвестная отправка не блокирует следующую независимую задачу.

- `tests/acceptance/task-workflow.cjs`: 28 сквозных сценариев.
- `tests/workflow-candidate.cjs`: 7 проверок сборки, совместимости и демонстрации.
- `node tools/task_workflow_demo.cjs`: happy / projection_recovery / unknown_notification. Вывод только агрегатный, без имён, ID, текста или ссылок. Во всех трёх сценариях один файл, один ответ и один API-вызов уведомления владельцу; unknown сохраняется как DEAD, не превращается в доставку.

## Данные и пределы готовности

Бизнес-схемы не меняются, новые листы не добавляются. Расширяется назначение «Снимки операций»: туда попадают планы/квитанции отправки поручений и команд доступа, включая адресата, имя/текст и прежнее состояние доступа. Для будущей установки этот объём нужно согласовать явно. Предыдущее разрешение на привязку ответов не заменяет его.

API_CONFIRMED и «Отправлено» означают подтверждённый ответ API, не физическую доставку. Unknown не означает «сообщение не отправлено». Автоматического сброса claim, удаления старых дублей, очистки receipts, TTL, ретроспективной рассылки или полноценного интерфейса ручного восстановления нет. Повторная ручная отправка требует решения по конкретной операции.

Остаются внешние условия: текущие права Sheets после OAuth revoke, проверка однозначной закрытой Drive-папки (legacy ищет её по имени), активные триггеры и реальное состояние очереди. ScriptLock не защищает от ручной сортировки между read/write. Эти условия нельзя считать выполненными по локальным тестам.

## Один следующий этап, когда владелец вернётся

1. **Проверить доступ и условия:** существующая авторизация, схема, однозначная закрытая папка, фактические триггеры. Не запускать initialize/setupAutomation и не отключать рабочие функции без согласования.
2. **Согласовать единый пакет:** один main, семь сохранённых файлов, указанное расширение технических снимков. До этого не добавлять apply-маршрут и не ставить новую версию в рабочий проект.
3. **Защищённая установка:** свежий review, полный encrypted backup, штатный GitHub environment approval, один PUT, независимый reread. Никаких необоснованных автоматических rollback.
4. **Ограниченная реальная приёмка:** только заранее согласованный тестовый аккаунт со студенческой ролью, искусственное поручение и маленький файл, выбранные закрытые ресурсы. Согласовать конкретные отправки и записи; реальные студенты и журнал в тест не включаются. Не использовать рабочий массовый poll/sendPendingTasks без ограничения набора.
5. **Проверить факт:** правильный адресат/ID, один файл, один ответ, верная задача, две API-квитанции и ручное подтверждение получения. Старые receipts не сбрасывать ради теста. Не устраивать реальные таймауты/ошибки на рабочих данных: fault injection остаётся локальным.
6. **Записать результат:** отдельно installation / API acknowledgement / подтверждение человеком. Только после этого считать рабочий маршрут принятым. Остальные блоки — расписание, консультации, журнал, ChatGPT/MAX — не объявлять включёнными.

Пока владелец без компьютера, действий не требуется. Подготовка этого пакета не меняет текущий бот, права студентов, календарь, триггеры или реальные файлы.
