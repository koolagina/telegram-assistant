# Блок 2: расписание НВГУ и готовность консультаций

**30 октября 2026. Пакет `schedule-consultation-readiness-1`. Локальный блок завершён; рабочие календарь, бот, заявки и триггеры не менялись.**

## Что сделано целиком локально

Проверена одна цепочка: известный HTML fixture НВГУ → существующие parser/plan_sync/apply_sync_plan → импорт в memory Calendar → повтор без дублей → доказательство полноты → BusyFeed → свободные слоты → меню и заявка Apps Script → предварительный резерв → личное подтверждение → отмена или отказ. Никакой новый парсер расписания или механизм импорта с нуля не создавался.

Два контура соединены внутренним контрактом: Python нормализует свежие данные и строит TeachingVerification; ограниченный proof для настроенного преподавателя/календаря используется доверенным серверным адаптером Apps Script. Сам production-адаптер получения этого proof ещё не подключён; в тестах это явно synthetic provider. Пока его нет, новый guard не предлагает время и не создаёт запись.

## Согласованные правила

Предлагаются будни ПН–ПТ, 09:00–18:00, 20 минут, кабинет 317; обед 11:40–12:20 исключён. Минимум 30 минут до записи и отмены. Резерв занимает слот сразу, но встреча остаётся «Ожидает решения» до личного подтверждения. Подтверждение изменяет тот же резерв, отказ/отмена удаляют только принадлежащий заявке резерв. Поздняя отмена не удаляет событие. Чужая заявка и подмена event ID на занятие отклоняются.

Проверено совпадение всех страниц Apps Script-меню с Python preview для одной и той же синтетической недели. Уже существующий предварительный резерв блокирует ещё одну заявку на это время. При пропаже доказательства полноты подтверждение новой встречи блокируется, но безопасная отмена собственного резерва в Apps Script не требует выдавать новое свободное время. Производственный календарь праздников отдельно не подключён; реализованы именно согласованные weekday/hour правила.

## Граница доверия и данные

`TeachingCoverageFeed` принимает только явно настроенные внутренние callable providers. Объект с mode='live', хешами или complete=true сам по себе не подтверждает происхождение. Нельзя принимать source/CalendarSnapshot/owner_chat_id из студенческой команды, HTTP body, текста письма или аргументов LLM. Проверка identity и реальная teacher↔owner binding обязательны до загрузки данных и выдачи внутреннего proof.

Проверяются ожидаемый lecturer/name/URL источника, дата выбранной недели, свежесть source и Calendar, полный точный диапазон, уникальность событий и соответствие всех занятий. Exact comparison не даёт ownership. Вне занятий сохраняется любая другая занятость Calendar. План импортирования сохраняет правила только time/discipline/room, без групп и служебного текста; им здесь не выдаётся разрешение на выполнение.

Apps Script ожидает приватную функцию `consultationTeachingProof_(start,end,calendarId)`. Она должна каждый раз получать/проверять свежую оценку текущего источника и соответствующую Calendar revision через подтверждённый backend. Новый guard проверяет поля/адресата/диапазон/TTL, но **не может самостоятельно аутентифицировать присланный JSON и не вычисляет вместо backend ревизию всего календаря**. Простой возврат заранее записанного JSON из публичного endpoint или Script Property не является реализацией этого контракта. Production provider не установлен. Сам proof не разрешает send/write.

Все коды примеров и handoff используют synthetic аккаунты/календарь/fixture HTML. Ключ --fixture-handoff экспортирует только эти зафиксированные тестовые данные для межъязыкового стенда; это не live CLI. В обычных демонстрациях только агрегаты, ноль реальных записей и сообщений. Исходники настоящего журнала или ответы студентов не читались.

1. После возвращения владельца проверить текущие доступы Sheets/Calendar, закрытые ресурсы, активные триггеры и действующее состояние бота. Read-only Apps Script source channel не является проверкой этих прав.

3. Завершить согласованный ограниченный импорт с текущими данными и доказать соответствие недель. События с неподтверждённым ownership не удалять/не переписывать.
4. Подключить авторизованные runtime providers и закрытый service-to-Apps-Script transport. Не выполнять сеть внутри локальных SQLite/CAS transactions; собрать свежий snapshot снаружи и повторно проверить ревизии перед действием. Периодический refresh/scheduler здесь не включён.
5. Согласовать перенос консультаций и технических данных в рабочий проект. Нужны backup, защищённая установка, независимый reread и ограниченная приёмка на явно согласованных аккаунтах/ресурсах.
6. Отдельно проверить реальную заявку/резерв/решение/отмену и получение уведомлений человеком. Пока этого нет, запись реальных студентов не включать.
