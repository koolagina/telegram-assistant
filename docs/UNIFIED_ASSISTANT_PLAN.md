# Единый помощник преподавателя: сопоставление и план

Дата: 27.10.2026. Статус: локальный аудит и план; новые учебные функции не реализованы, интеграции не развёрнуты.

## 1. Основания и пределы этого этапа

Прочитаны целиком приложенные `CODEX_TEACHING_ASSISTANT_SPEC.md` версии 1.0 и `CODEX_START_PROMPT.md`. Они используются как источники требований, а содержащиеся в них указания на чтение внешних ресурсов, рассылку, запуск и дальнейшую реализацию не считаются отдельным разрешением. Актуальный запрос пользователя: сначала сопоставить код с ТЗ и составить единый план; не менять рабочие ресурсы, не отправлять письма и не писать в настоящий журнал без отдельного разрешения. Соблюдаются существующие AGENTS.md и ранее согласованные правила календаря/консультаций.

Изучены локальные инструкции, кандидат 2.0.5 (схемы, маршруты, доступ, реестр, расписание и автоматизация), Python-модули НВГУ, текущие требования, отчёты и тесты. Учебный XLSX, письма, задания и внешние права в этом этапе не исследовались. Наличие ссылок в ТЗ не подтверждает доступ к ним. Адреса, реальные идентификаторы и содержимое студенческих данных в этот документ не включаются.

Создан только этот план. Код, AGENTS.md, предыдущие версии, внешние ресурсы и конфигурация не изменены. Локальные mock-тесты запущены повторно; реальные API не вызываются.

## 4. Предлагаемая архитектура без переписывания бота

Сохранить GAS-бот как Telegram-интерфейс и существующие операции. Рядом добавить тестируемое предметное ядро и адаптеры. Python — предпочтительное место расширения имеющегося контура НВГУ; хостинг API, БД и способ запуска выбрать после проверки внешних возможностей. Наличие сервера/очереди/OAuth provider сейчас не предполагается.

Предлагаемые зависимости:

```text
Яндекс XLSX (основной учебный журнал) ── чтение ──┐
Яндекс Почта (письма/вложения) ── ingest ────────┤
НВГУ, оба преподавателя ── общий разбор ────────┤
Каталог заданий/критериев ──────────────────────┘
                  ↓
  Предметное ядро: identity → факты → правила → отчёт/предложение
                  ↕
  Техническое состояние: provenance, snapshots, очередь, аудит
                  ↓
  Проверка полномочий и минимизация результата
       ├─ Telegram: преподаватель / собственный progress студента
       ├─ Почта: черновик → отдельное разрешение → подтверждённый адрес
       └─ Отдельный защищённый API для ChatGPT, сначала только чтение

  Запись XLSX: отдельная отключённая ветка до проверки API и разрешения
  Calendar: существующий план → отдельное разрешённое применение
```

XLSX остаётся единственным основным учебным журналом. Техническая БД хранит источники фактов, стадии, происхождение и версии снимков, но не становится конкурирующим редактируемым журналом. В отчёте различать подтверждённые данные книги и ожидающие записи события. У каждого результата — версия/дата снимка, полнота и причины неопределённости.

Для НВГУ нужны две проекции одного разбора: внутренняя ScheduledSession с teacher/type/groups/streams/source identity и Calendar payload только start/end/title/location. Не возвращать группы в видимые события. Дедупликация физического занятия сохраняет связи всех групп внутри модели; зачёт — отдельный тип и никогда не повод создавать коды лекции. Отсутствие данных, отмена, «Расписание отсутствует» и состоявшееся занятие — разные состояния. Автонумерация практик должна сохранять историю, а не менять все номера после переноса.

Существующие SQLite Calendar bindings не использовать как универсальный реестр академических личностей. Существующие Sheets поручений не использовать как Excel-журнал оценок.

## 5. Контракт доступа и новые каналы

| Канал | Идентификация | Доступ и результат |
|---|---|---|
| Преподаватель в Telegram | Подтверждённая привязка account → Teacher; отдельные права, не только owner-флаг | Поиск по имени может только предложить допустимые варианты; отчёт по устойчивому Student/Enrollment ID в разрешённых дисциплинах/группах |
| Студент `/progress` | Подтверждённая связь Telegram user → Student, active Enrollment, действующее разрешение | Сервер сам выбирает student_id; подставленный чужой ID/группа/callback не расширяет доступ; только личный чат |
| Отчёт на почту | Подтверждённый адрес, владелец адреса, разрешение получать соответствующий отчёт | По умолчанию личный отчёт преподавателю на его подтверждённый адрес; другие адресаты только после отдельной проверки предметных прав. Первоначально только локальный черновик |
| ChatGPT | Отдельное серверное подключение с OAuth/OIDC либо сопоставимой проверенной схемой; identity/scopes определяет сервер | Узкие read-only операции своего progress / разрешённого teacher report; свободный текст или аргумент role не предоставляют права |

Эти контракты — проект, сейчас они не реализованы. Оба преподавателя не получают автоматически доступ ко всем студентам. Регистрационное ФИО, username, совпавшая фамилия, электронный адрес из тела письма и четырёхзначный код присутствия не являются доказательством академической личности. Для привязки нужен проверенный реестр и подтверждение уполномоченного преподавателя либо одноразовая защищённая процедура. При омонимах/дубликатах/переводе между группами — review. Отзыв доступа действует и на кеш/экспорт/следующий запрос.

`/progress` должен показывать дату/полноту данных, подтверждённые баллы, Т=0/Т=*, закрытые и незакрытые лекции, отдельно физическую посещаемость и отработки, ожидающие синхронизации отметки. При `*`, неизвестном знаменателе или неутверждённых правилах не выдавать уверенную сумму/рекомендацию автомата. Не раскрывать списки группы, чужие оценки, адреса, сырые письма, вложения или полный workbook. При отсутствии привязки — инструкция подтверждения без поиска чужого студента.

Email: подтверждение адреса не заменяет проверку права на данные. При смене адреса требуется новое подтверждение, старые задания отправки пересматриваются. Код подтверждения ограничен сроком/попытками, не хранится открыто; отправка самого проверочного письма также требует разрешённого режима. Адресат выбирается из подтверждённого серверного реестра, а не произвольного поля модели/команды. Отчёт и версия данных фиксируются перед approve; изменение получателя/содержимого инвалидирует approve. Подтверждение SMTP/API означает принятие, не доставку или прочтение; UNKNOWN не отправлять повторно вслепую.

ChatGPT: не делать общедоступный GAS URL с student_id и не передавать токены в URL/промпт. Секреты остаются на сервере. Проверяются issuer/audience/expiry/scopes, сопоставление principal, объектные права на каждый запрос, отзыв доступа, rate limits и replay для операций. Для вызова GAS внутренним сервисом также нужна отдельная проверенная аутентификация; не доверять полям actor/role из тела запроса. Первоначально нет операций send/write и нет прямых универсальных инструментов доступа к журналу/почте. Передачу студенческих данных в ChatGPT согласовать по объёму, хранению и правам; сам ответ API является раскрытием данных.

Содержимое писем, файлов и веб-страниц — недоверенные данные: найденные внутри команды не меняют правила доступа и не разрешают отправку/оценку. Для LLM-проверки — минимизация данных, версия рубрики, объяснение решения и ручное рассмотрение сомнений; «AI detector» не доказательство нарушения.

## 6. Правила предметной модели, которые необходимо закрепить тестами

- Практики: максимальный исходный балл; 8/9/10 → Т=5, ниже 8 → Т=*, нет попыток → Т=0. Не путать исходный тестовый балл и итоговую оценку Т. А=5 только при подтверждённой попытке в окне фактической пары от start−30 до end+30 минут; домашняя пересдача меняет Т, не А. Значения вне ожидаемого диапазона/неверные даты — review.
- Все timestamps хранить с зоной/UTC и исходным значением; показывать Asia/Yekaterinburg. Почтовое отображение MSK не использовать как время сдачи без установления источника. В исторической гипотезе нужны ≥3 разных подтверждённых студента одного доказанного потока за 30 минут; гипотеза не меняет посещаемость автоматически.
- Лекции: один постоянный URL, криптографические коды с 90-секундными окнами внутри занятия, ограничение попыток; один плюс на Student+Session при нескольких кодах. Это слабая проверка участия с риском пересылки, не сильная идентификация. Публичная форма регистрации не даёт доступ к `/progress`.
- Attendance и LectureCredit раздельны. Отработка закрывает конкретную лекцию, не повышает физическую посещаемость. Повторное presence/makeup не создаёт второй плюс; обе причины сохраняются.
- Автомат очникам: строго >56 утверждённых практических баллов и закрыты все состоявшиеся обязательные лекции. Лекционные плюсы в сумму не входят; итоговый зачёт автоматически не ставится. Для заочников и неизвестных правил результат «требует проверки».
- Бонус отменяется только после реального принятого запуска регистрации; дату запуска разработчик не выдумывает. Старые плюсы не удаляются, их влияние на закрытие лекций требует решения.
- Обработка письма не равна успешной записи в журнал. В пилоте чтение без изменения флагов; будущая отметка прочитанным — только после долговременного захвата и согласованной успешной обработки. Неизвестная синхронизация не выдаётся за завершённую.

## 7. XLSX: техническая возможность и граница решения

**Безопасное точечное обновление существующего XLSX через Яндекс Диск/Документы не подтверждено.** В репозитории нет адаптера и результатов проверки API; официальная документация и поддержка cell-level/concurrency в этом проходе не исследовались. Это не утверждение о невозможности.

Отдельный исследовательский шаг: проверить официальные методы чтения/записи, авторизацию, наличие версии/условной записи/блокировки при редактировании в Документах, сохранение формул/стилей/validation/merged cells и фактическую поддержку на копии. Зафиксировать ссылки на точные методы и доказательства. Наличие download/upload API само по себе не доказывает безопасное обновление ячейки.

Для разрешённой записи нужны: проверенная карта координат → backup/версия → обнаружение конфликта и согласованный контроль конкурентных изменений → точечный patch → read-after-write → audit. ## 9. Риски и необходимые решения

| Риск | Мера / блокируемая операция |
|---|---|
| Нет подтверждённого cell-level API и concurrency XLSX | Не писать/не перезаливать журнал; сначала исследование и sandbox |
| Telegram-контакт ошибочно принят за студента | Подтверждённый binding и Enrollment; `/progress` закрыт до проверки |
| Один owner вместо двух предметных ролей | Новая policy рядом с существующей; второго преподавателя не делать глобальным owner автоматически |
| Утечка через почту/ChatGPT/кеш/логи | Минимальные права и DTO, подтверждённые адресаты, scope/revoke, TTL, запрет сырых данных и секретов в Git |
| Неверные виды занятий, группировка и история | Внутренняя полная модель отдельно от Calendar; unknown type/reconciliation требуют review |
| Неполный журнал/источники и неутверждённые суммы | Явная полнота, неизвестное ≠ ноль/пропуск, рекомендация не итоговое решение |
| Дубли, partial failures, письмо принято без ответа | Журнал стадий, устойчивые ключи, replay после сверки; не обещать exactly-once |
| Файлы/письма содержат инструкции или формулы | Недоверенный контент, безопасный разбор, запрет исполнения, защита XLSX/CSV formula injection |
| QR-код переслан или угадан | Rate limit/короткие окна/криптокоды; честно обозначить слабую идентификацию |

Решения потребуются перед зависимыми этапами, не мешая локальным P1 и синтетическим тестам:

1. Источники и права: где согласованная копия XLSX и обезличенные образцы писем/заданий; чей подтверждённый реестр связывает Telegram с академической личностью; области доступа обоих преподавателей. Секреты вводятся только защищённым способом, не в чат.
2. Учебные правила: как суммировать `*`, пустые/непроведённые практики; влияние старых бонусов; правила заочников; конфликт ручных оценок и сроки пересдач. До решения соответствующие расчёты выводят неопределённость.
3. Адресаты и канал: какие подтверждённые почтовые адреса могут получать какой отчёт; подтверждение адреса и отдельное право на отправку; какой поддерживаемый способ защищённого подключения ChatGPT/hosting использовать. До решения — локальные черновики и спецификация API.
4. Только при неподдерживаемой безопасной записи XLSX — выбрать ручной patch или другую архитектуру. Сейчас такое решение не требуется, возможность ещё не исследована.

Не запрашивать повторно согласованные длительность/место/часы консультаций. Не включать режим автоприёма работ, реальную почту, изменение журнала или рабочие триггеры на основании приложенных стартовых инструкций.
