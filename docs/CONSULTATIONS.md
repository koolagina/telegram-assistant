# Консультации: согласованный сценарий и кандидат 2.0.5

Правила согласованы владелицей 27.10.2026: 20 минут, очно в кабинете 317, рабочие дни 09:00–18:00, обед 11:40–12:20, запись и отмена минимум за 30 минут, личное подтверждение каждой встречи. Часовой пояс — Asia/Yekaterinburg.

## Студент

`/consultations` открывает три кнопки:

1. **Записаться** → день на ближайшие 7 календарных дней → свободное время → тема → проверка заявки → «Отправить заявку». Слоты выдаются по 10 на страницу с кнопками перехода; шаг 20 минут. Данные календарей читаются целиком на выбранный день, а не отдельным запросом для каждого слота.
2. **Мои заявки** → последние 10 своих заявок, время, тема и статус. Для активной заявки есть «Отменить заявку». Для более старых записей и legacy длинных ID интерфейс пагинации пока не реализован.
3. **Правила консультаций** → место, длительность, часы, обед, сроки и порядок подтверждения.

Студент видит только свои записи. Чужие cancel/owner callbacks отклоняются. Доступ должен быть «Одобрен», callback — из private chat с совпадающими from.id и chat ID.

Пока студент выбирает время или вводит тему, Calendar не меняется. При отправке заявки бот повторно проверяет часы, срок, занятия и календарь, создаёт предварительное занятое событие и отправляет уведомления студенту и владелице. В названии явно указано «Ожидает подтверждения». Это не окончательное одобрение встречи.

Черновик диалога действует 30 минут. `/cancelbooking` удаляет черновик без создания заявки. Переход к другой команде, например `/tasks`, прекращает заполнение; вложения сохраняют обычный маршрут обработки поручений. Уже принятую тему нельзя повторно превратить в ответ на поручение: ключ сообщения и снимок диалога сохраняются в техническом листе «Снимки операций». Старые submit-кнопки не подтверждают новый черновик.

Команды для совместимости: `/consult YYYY-MM-DD HH:MM тема`, `/myconsultations`, `/consultationrules`, `/cancelconsult ID`. Длительность 20 минут; другая длительность отклоняется.

## Владелица и календарь

Уведомление о новой заявке содержит «Подтвердить» и «Отклонить». Можно также использовать существующие `/consultations`, `/approveconsult ID`, `/rejectconsult ID причина`.

- **Подтверждение:** ещё одна проверка занятости, исключая только собственное предварительное событие с проверенной меткой заявки. Обновляются название и описание того же события, новое событие не создаётся. Данные встречи: 20 минут, кабинет 317.
- **Отказ:** удаляется предварительное событие только с меткой этой заявки, запись в Sheets получает «Отклонена». Уведомляются обе стороны.
- **Отмена студентом:** только своей активной заявки и минимум за 30 минут. Удаляется соответствующее событие, статус — «Отменена», уведомляются обе стороны. Позднее бот предлагает связаться с преподавателем; отмена подтверждённой встречи владельцем через отдельную кнопку пока не добавлена.

Ассистент по расписанию читает этот же Calendar, поэтому увидит предварительную запись после своей синхронизации. Бот отправляет отдельное Telegram-уведомление сразу в рамках обработки. Его принятие сервером Telegram, чтение человеком и реакция другого ассистента — разные события. Срок обновления стороннего ассистента здесь не проверялся; новые произвольные напоминания Calendar не выставлялись.

## Источник занятости и безопасная конфигурация

Значения настоящих идентификаторов/секретов в код не добавлены. Нужны отдельные тестовые ресурсы, описанные в аудите: test bot, тестовая книга и календарь. Для проверки занятий требуется один из вариантов:

- `ASSISTANT_TEACHING_CALENDAR_ID` — отдельный проверенный календарь, содержащий все занятия;
- либо `ASSISTANT_CALENDAR_HAS_ALL_LESSONS=true` — явное подтверждение в Script Properties, что целевой `ASSISTANT_CALENDAR_ID` уже содержит все занятия.

Владелица уточнила: часть занятий уже внесена, часть отсутствует. Значит, пока нельзя включать флаг полноты — сначала нужен проверенный импорт недостающих занятий из НВГУ без удаления или дублирования уже существующих записей. Само чтение этого Calendar другим ассистентом не подтверждает полноту занятий. Пока источник не настроен, подбор слотов и создание заявок **отказывают**, правила и список уже существующих заявок доступны. Не устанавливать флаг полноты только для прохождения проверки.

В текущем кандидате рабочие дни означают понедельник–пятницу. Праздники, отпуск, командировки и иные нерабочие дни должны быть отмечены занятой записью на весь день в проверяемом календаре; отдельный производственный календарь/переносы выходных ещё не подключены. Это ограничение требуется проверить перед приёмкой.

## Состояния и восстановление

Схема существующего листа «Заявки на консультации» (11 колонок) не меняется. Добавляются значения статусов:

`Создаётся предварительная запись` → `Ожидает решения` → `Подтверждена`.

Отмена/отказ проходят через `Отмена выполняется` / `Отклонение выполняется`, затем `Отменена` / `Отклонена`. Существующие validation rules в тестовой копии необходимо проверить отдельно, без слепой миграции.

- Стабильный ID заявки зависит от chat/message ID, у диалога — от сообщения с темой.
- Calendar operation ledger и метка `[assistant:CONSULT:<ID>]` связывают событие с заявкой. Потеря ответа после create или записи event ID не создаёт второго события.
- Удаление допускается только после проверки метки. Если Calendar подтвердил удаление, но ответ потерялся, повтор завершает статус и уведомления без повторного удаления чужого события.
- Уведомления используют существующий outbox с ключом действия/адресата. UNKNOWN/SENDING без сохранённого message_id требуют сверки; exactly-once внешней доставки не обещается.
- Смена статуса/уведомление не являются общей транзакцией с Calendar. Ошибки доступа, неполные данные и неопределённые результаты оставляются для durable retry/операторской сверки. Промежуточные статусы не выдаются за успешное бронирование.
- Автоматического срока снятия неподтверждённого резерва нет: это правило владелица пока не задавала. Удаление по отказу/отмене реализовано; фоновый cleanup и лимит активных заявок на студента требуют отдельного решения.
