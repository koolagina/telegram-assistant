# Решение по консультации: локальный кандидат

29.10.2026. Это отдельная offline-модель поверх существующих правил консультаций, не новый механизм записи в Google и не замена GAS-кандидата. `src/telegram_assistant_v2_0_5_candidate.gs`, его 11 колонок заявок, Calendar и рабочий бот не изменены.

## Сценарий

1. Карточка: ID, дата/время Екатеринбурга, 20 минут, кабинет 317, статус **локальной** модели. Кнопки «Подтвердить», «Отклонить», «Предложить время».
2. Выбор действия создаёт только частный intent, привязанный к ревизии заявки. Перед выбором времени используется `/consult_propose REF YYYY-MM-DD HH:MM` — это пока интерфейс локального обработчика, а не установленная команда рабочего бота.
3. Отдельный экран спрашивает «Подтвердить действие?»; подтверждение действует 5 минут. «Назад / отменить» инвалидирует intent, не отменяет саму заявку и не снимает резерв. Пять минут относятся к кнопке подтверждения, **не** к сроку жизни предварительной календарной записи.
4. Финальное нажатие повторяет проверки и атомарно сохраняет локальный статус, plan и отметку intent. Результат всегда `planned`, `execution=not_executed`. Успеха API или доставки здесь нет.
5. Повтор и перезапуск возвращают тот же plan при наличии текущих прав владельца. Конкурирующее решение по старой ревизии отклоняется. Сбой SQLite откатывает весь набор изменений.

[Пример диалога](CONSULTATION_ACTIONS_DEMO.md), воспроизводится `python tools/consultation_demo.py`; все записи/ID искусственные, БД временная, сети нет.

## Правила и данные

`tools/consultation_actions.py`: `Booking`, `BusyEvent`, `BusySnapshot`, `ConsultationActions.preview/confirm/cancel`. `tools/consultation_requests.py`: карточка и **явные локальные handlers**, которые записывают intents/plans. `reference/resolve` проверяют актуальные права и ревизию. Не принимать identity, роль, calendar completeness или ownership из текста пользователя.

- `personal.read` на настроенного владельца до/после чтений; пересланная кнопка, другой преподаватель, студент и отозванная binding не дают доступа. Trusted eligibility callback повторно проверяет доступ студента при approve/propose. Это контракт интеграции, не реализация реальной student registry/authentication.
- Время aware, Asia/Yekaterinburg, Пн–Пт, 09:00–18:00, длительность 20 минут, нет пересечения с обедом 11:40–12:20. Предложение нового времени — минимум за 30 минут. Подтверждение ранее поданной заявки возможно ближе чем за 30 минут, если начало ещё не прошло: новый срок подтверждения владельцем не придуман.
- Полный свежий snapshot занятости и занятий обязателен; covered range включает исходный резерв и предлагаемый слот. Observed time не заменяется временем клика, возраст ≤5 минут проверяется после чтения. Неполнота/сбой/будущая дата/неизвестное владение блокируют план, включая отказ: это намеренно консервативное ограничение локальной модели.
- Только один event с точным `event_id`, trusted `consultation_id`, исходными start/end является своим резервом. Название/кабинет/похожее время недостаточны. Другие события не исключаются из занятости. Интервалы полуоткрытые, соседние встречи разрешены.
- Approve планирует **update того же event**, без create. Reject — delete только этого проверенного event. Оба содержат expected hold и ревизию, два отдельных notification-намерения: студенту и владельцу. Это не готовые сообщения с проверенными Telegram-адресатами.
- Propose сохраняет первоначальные время, статус ожидания и резерв; планирует только предложение и уведомление владельцу. Согласие студента, атомарная замена резерва и финальное подтверждение переноса ещё не реализованы. Автоматически двигать событие нельзя.

SQLite WAL/FULL, private directory/file, namespace+owner identity, `BEGIN IMMEDIATE`, уникальный intent token. `add/booking/plans` — **внутренние доверенные** fixture/operator методы, не публичный API. Store разрешён только для локальных фикстур: не загружать в него рабочую таблицу и не использовать изменённый локальный статус как свидетельство исполнения внешнего действия. Нет cleanup/автоматического удаления истории, переключения старых DB, отправок или фоновых задач.

## Что требуется до подключения

- Авторитетный live snapshot исходных заявок, стабильная ревизия/связь с реестром студентов и честная полнота занятости после проверенного импорта НВГУ. Не принимать настройки полноты из пользовательской команды.
- Отдельный dispatcher подтверждённых Telegram updates. Эти handlers **нельзя вызывать из `ReportWorker.prepare_fresh`**: тот предназначен для повторяемой подготовки read-only ответа под claim, а здесь есть локальная запись. Текущий report adapter/worker и `/decisions` остаются read-only и не маршрутизируют `con:*`.
- Отдельно проверенный executor: повторная авторизация, сверка актуальной заявки/ownership/calendar preconditions непосредственно перед операцией; durable operation claim до возможного API side effect, reconcile после uncertain outcome, обновление authoritative Sheet только по подтверждённым результатам. Plan ID/приватный token не разрешение на реальное исполнение. Не повторять blind create/update/delete/send.
- Отдельные outcomes Calendar/студент/владелец. Сбой уведомления не должен повторять изменение встречи, API success не доказывает доставку. Pending/unknown не переводить в завершённые.
- Разрешённая sandbox-приёмка на отдельном боте/календаре/книге с резервированием. Настоящие ресурсы и триггеры не задействованы, развёртывание требует отдельного согласования.

## Локальная проверка

`python -m unittest discover -s tests -p 'test_consultation*.py'`: 30 тестов (23 core +7 UI/demo). Проверены две одновременно открытые connection/threads, перезапуск, повтор, ревизии, rollback plan insert, свежесть/полнота/ownership, изменение занятости/доступа во время чтения, expiry, границы слотов, private plain-text UI/поддельные кнопки. Реальных Calendar/Telegram/Sheets интеграционных тестов не было.
