# Кандидат восстановления файлов legacy — 30.10.2026

Статус: **только локальный кандидат, не установлен**. Google relay по-прежнему разрешает только предыдущие2исправления, этот патч не входит в его write allowlist. Рабочий source остаётся подтверждённым run40936525532. Кандидат2.0.5 и исходные архивы не изменены.

## Воспроизведение и изменение

Legacy processMessage_ проверяет дубли по строкам «Ответы»/«Входящие», но вызывает storeFile_ до appendRow. Если Drive create успешен, а appendRow падает, следующий poll не видит строки и создаёт второй файл. При неизвестном create исходе прежний catch ещё и записывал ответ без вложения, позволяя продвинуть offset.

Сначала3tests воспроизвели проблемы (red), затем добавлен локальный рецепт tools/clasp/legacy-file-recovery.cjs: меняет только точный ранее проверенный блок storeFile_. Review diff — patches/legacy-file-recovery.patch (diff отдельной функции, не команда замены полного проекта). На8файловый source из Google рецепт применён только в памяти:7files/остальной основной код без изменений, совокупный синтаксис PASS.

В Script Properties отдельный ключ KULAGINA_LEGACY_FILE_V1_<chat>_<message> хранит JSON version/status/file_id/type/link. Перед createFile записывается SENDING, после получения ссылки — SAVED. На повторе SAVED используется прежняя ссылка; несовпадение идентичности/повреждённый receipt/SENDING останавливают создание. На сбое создания/фиксации receipt исключение доходит до существующего poll, offset не продвигается. Текст/слишком большие файлы сохраняют прежние форматы; файл не публикуется, sharing не меняется; числовые индексы/заголовки/9полей ответа не меняются. Статусы поручений не менялись этим патчем.

## Ограничения до установки

- SENDING — неизвестный исход, не доказательство созданного/отсутствующего файла. Не удалять/reset маркер автоматически. Нужна сверка фактического Drive файла/ответа и явное решение владельца для привязки. Надёжного восстановления по сохранённому Drive ID до acknowledgement здесь нет.
- Такой update блокирует остальную legacy очередь; polling может повторять уведомления владельцу. Этот патч предотвращает дубли/ложный успех, но не добавляет durable inbox/dead-letter/recovery UI. До live установки нужен порядок разблокировки без потери update.
- Receipts не очищаются: удаление по TTL может вернуть дубли. Script Properties имеет квоты; необходимы оценка объёма и контролируемая архивация/ledger до длительного использования.
- Сериализация опирается на существующий ScriptLock в pollTelegramUpdates; storeFile_/processMessage_ нельзя параллельно вызывать напрямую или из нового handler без общего lock. Это ограничение не устранено новым патчем.
- Не проверяется последующее ручное удаление файла Drive. Нет автоматического пересоздания. Поиск папки по имени пока прежний: ambiguous folders остаются отдельным риском.
- Не исправлено падение после appendRow до обновления поручения/уведомления: существующий duplicate check может пропустить завершение этих шагов. Нельзя объявлять весь обработчик exactly-once или полностью восстановимым.

Следующий приоритет внутри этого же дефекта: безопасный read-only recovery report для SENDING и согласованный способ завершения, затем решить durable ledger/квоты. Установка требует отдельного конкретного согласования; прошлое разрешение на2legacy исправления не расширять.
